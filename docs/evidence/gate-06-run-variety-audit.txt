CYBERPUN-17-14-t4 (PR 4) -- gate 6 audit trace: run-to-run variety
===================================================================

Scope: "every run differs -- two consecutive RUN AGAIN runs with different
cities and start junctions" (gate 6).

Method
------
Re-read `GameScene.startNewRun()` (CYBERPUN-17-13 PR 3) and
`RunSpawnSelector` against gate 6's two named claims:

1. A different starting junction per run: `startNewRun()` draws a fresh
   `WorldSeed` via `UInt64.random(in:)` before every RUN AGAIN, and
   `RunSpawnSelector.selectSpawnTile(seed:)` is a pure function of that
   seed, so a fresh seed lands on a different street-intersection junction.
   Already covered by `GameStateMachineTests
   .test_startNewRun_drawsADifferentSeed_everyConsecutiveInvocation` and
   `.test_startNewRun_spawnsAtADifferentStreetIntersection_everyConsecutiveInvocation`
   (20 consecutive invocations, junction set size > 1). No offender found.

2. A different city: this is the claim neither of those two existing
   tests actually checks. Both assert on the *seed* (a `Set<UInt64>` of
   size 20) or the *junction tile* (`RunSpawnSelector.selectSpawnTile`'s
   own output) -- a hypothetical bug confined entirely to
   `RunSpawnSelector`'s own hash stream (wrong junction, but the same city
   everywhere else, e.g. an accidentally-fixed salt) would still pass both
   existing tests while failing gate 6 outright, since the *city* the
   player actually walks through would not have changed.
   `RunVarietyTests.swift` (new, this PR) closes that gap directly:
   `test_consecutiveRunAgainInvocations_produceGenuinelyDifferentCityLayouts_notJustADifferentJunction`
   fingerprints a real tile neighbourhood (13x13 tiles) around each run's
   own spawn junction via `CityLatticeGenerator.classify` **plus every
   building `BuildingPlacement.generate` places on the blocks that window
   covers**, and asserts that **every consecutive pair** of 10 RUN AGAIN
   runs differs -- not merely that some pair somewhere in the sequence
   does (PR #67 review: gate 6's wording is "two consecutive RUN AGAIN
   runs", and a "distinct count > 1" spelling would pass while runs 2-10
   were byte-identical). The per-lot building selection is in the
   fingerprint for a reason: `RunSpawnSelector.selectSpawnTile` always
   returns `blockN * period + junctionCentreOffset`, so the street/lot
   lattice *structure* of this window is invariant by construction and a
   tile-kind-only signature would be both narrower than the gate's claim
   and coarse enough for two genuinely different seeds to collide. The
   existing junction-only claim is also restated in the same file
   (`test_consecutiveRunAgainInvocations_doNotAllShareOneStartJunction`,
   named for what it checks: a bounded candidate set makes two seeds
   sharing one junction a rare but genuine outcome, so that one stays a
   "not all the same" assertion) so both halves of gate 6's wording live
   together.

One deliberate accepted carve-out, unchanged by this PR and recorded
before this story began (AGENT.md/CLAUDE.md's own `CYBERPUN-17-13` entry):
the very first PLAY of a process launch still reaches `.gameplay` through
the seed-neutral `transition(to:)`, not `startNewRun()`, so a player who
launches, plays one run, dies and force-quits gets the identical city and
junction on every fresh launch. Gate 6's wording ("every run differs")
covers RUN AGAIN, which this PR's own scope is limited to auditing; the
first-PLAY carve-out is a pre-existing, explicitly-recorded, not-yet-human-
accepted product question this PR does not reopen or resolve.

Finding: no offender
---------------------
Both of gate 6's named claims hold for RUN AGAIN, confirmed by the
existing `GameStateMachineTests` coverage plus this PR's new
`RunVarietyTests.swift`, which is the first test in this codebase to
classify the actual generated tile layout (not just the seed or the
junction coordinate) across consecutive runs. No production code change
was needed for gate 6.

What this audit does NOT evidence
-----------------------------------
This is a code-level/in-suite check -- it is not a recording of a real
simulator run. A human (or the platform's runtime-probe pipeline) still
needs to capture `gate-06-run-variety.png`: two consecutive RUN AGAIN runs,
side by side, visibly showing a different city layout and a different
starting junction.

Probe coverage for that capture (PR #67 review)
------------------------------------------------
Gate 6 was previously the one gate whose runtime evidence was deferred with
no owner -- no journey tagged `CYBERPUN-17-14` captured anything gate 6
could be reviewed from, so the probe had nothing to execute for it on this
story's closing PR. `.mothership/journeys/death-and-high-scores.json` (long
since tagged `CYBERPUN-17-14` for gate 2, and the only journey in the tree
that taps RUN AGAIN and drives a second full run) now takes a gameplay city
frame in each of its two consecutive runs -- `gate-06-run-variety-run-1-city`
right after PLAY and `gate-06-run-variety-run-2-city` right after the
RUN AGAIN tap, both at the first gameplay frame of their own run so the
camera sits on that run's own spawn junction in each. The outstanding
literal capture above is now a side-by-side human/vision review of that
pair, rather than work with no journey behind it.
